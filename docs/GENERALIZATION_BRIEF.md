# 汎用化の検討用資料（別チャットへの引き継ぎ）

このリポジトリ（gov-movie）の「動画を作る仕組み」と、そこに至るまでの「企画・事例収集・データ調査のノウハウ」を、外に切り出して汎用化するための検討資料。
**新しいチャットでは、まずこのファイルを読ませ、続けて「9. 新しいチャットで最初に決めたいこと」から話を始める。**
（2026-10-15 時点。リポジトリ: `kumechang/gov-movie`、作業ブランチ `claude/dreamy-bell-rwvipw`、動画の控えは `videos` ブランチ）

## 0. 一言でいうと

- いまの仕組みは「**テーマ YAML を書けば、検証 → 地図・映像 → 音声 → 投稿文まで1コマンド**」。エンジン（`src/`、約5,100行）は動く。
- ただし「国名だけ入れれば自動」ではない。**YAML を書くところ（企画・台本・場所選び・写真選び・文言の検証待ち・見た目の微調整）に、毎回、人（ユーザー）とAIの対話が要る。** 実は、価値の大部分はそこ（ノウハウ）にある（3章）。
- 汎用化とは、①エンジンを切り出す、②データの取り方・検証のルールを部品にする、③**企画〜調査の進め方（ノウハウ）を、再利用できる形にする**、の3つ。③を後回しにすると、エンジンだけ汎用になっても、使える人が増えない。

## 1. いまの仕組み（何が動いているか）

### 1.1 全体の流れ

```
[人＋AI] 企画・事例分析・型の決定        … docs/FORMATS.md, docs/SERIES.md
   ↓
[人＋AI] 題材とデータの調査（ライセンス確認含む） … docs/prep/*.md, data/*.csv
   ↓
[AI] テーマ YAML を書く                   … themes/<id>.yaml（書き方: docs/THEME_SPEC.md）
   ↓                                        ここまでが「手作業（対話）」
python3 src/run.py themes/<id>.yaml        ここから1コマンド
   ├ データ取得・検証（外務省/e-Stat/Wikipedia/Commons） … mofa.py, estat.py, facts.py
   ├ 地図（国の形・州・国境線から30km帯など）         … world.py, geo.py
   ├ ナレーション生成（VOICEVOX）                    … narration.py
   ├ 効果音・音声ミックス                           … audio.py
   ├ 映像（1080×1920、フレームごとに Pillow で描画）  … render*.py → ffmpeg
   ├ 音量調整（loudnorm）
   └ 投稿文（post.md：タイトル・概要欄・固定コメント）
   ↓
[人] 見て直す → TikTok へ手で投稿（自動投稿はしない）
```

### 1.2 テンプレート（動画の型）

| template | 内容 | 状態 |
|---|---|---|
| `prefecture_map` | 都道府県の地図ランキング | 実装済み（離婚率） |
| `ranked_list` | 一覧型（grid / scroll / steps） | 実装済み（出生率など） |
| `tier_board` | 段階ボード（国をレベル別に） | 実装済み（G20の危険レベル） |
| `place_vs_risk` | 場所×危険情報（今回のシリーズ） | 実装済み（トルコ・カンボジア・フィリピン・エジプト・タイ・バリ島） |
| 推移の棒グラフ／場所×年代／企業プロフィール | | 未実装（`docs/FORMATS.md`） |

### 1.3 コードの構造（汎用化の目で見た所見）

| 層 | ファイル | 汎用化しやすさ |
|---|---|---|
| 設定の読み込み・検証 | `loader.py`, `theme.py`, `spottheme.py`, `listtheme.py`, `tiertheme.py` | テンプレートごとに別クラス。共通の「検証つきテーマ」の抽象は薄い |
| データ取得 | `estat.py`, `fetch_estat.py`, `mofa.py`, `facts.py`, `browser.py` | データ源ごとに独立。**検証（2系統照合・原文一致）の考え方は共通化できる**が、実装は個別 |
| 地理 | `world.py`, `geo.py` | Natural Earth（パブリックドメイン）。国・州・国境線。再利用しやすい |
| 描画 | `render.py`, `render_list.py`（約1,050行）, `render_spot.py` | 最も重い。**グローバル状態**（`rl.T`, `STYLE`, `FONT_PATH`）に依存し、同時に複数動画を扱えない。日本語の画面文言の一部がコードに残る（例:「どこ？」「レベル」） |
| 音声 | `narration.py`, `audio.py` | VOICEVOX 前提。声・クレジット表記は YAML（`voice.credit`）。話者を変えたら表記も変わる |
| 実行 | `run.py` | テンプレートごとの分岐 |
| テスト | `tests/`（69本） | 検証ロジックはよく守られている。描画は静止画の目視が中心 |

**切り出しの時に効きそうな既存の設計**
- 「`src/` にテーマ固有の文言を書かない。新しい動画 = YAML を足すだけ」（CLAUDE.md の作業ルール）。
- 「検証できていない数字を動画に載せない」を、**コードで強制**している（例: 公式ページの文言が一致しなければ動画を作らない）。これが最大の資産。
- 恐怖演出などの見た目は `style` で切り替え（バリ島編で、恐怖演出なしの落ち着いた見た目に切り替えられることを確認）。

**負債・制約**
- 描画のグローバル状態、日本語文言の一部ハードコード、英語など他言語は未対応（`docs/SERIES.md` 9章：日本語10本の後に判断）。
- 環境依存：フォント（日本語・キリル文字は出るが、**タイ文字は出ない**：写真の作者名が文字化けする）、VOICEVOX（Linux x86_64 用の配置スクリプト。Mac は未検証）、ヘッドレス Chromium。
- 1本の書き出しに約8〜10分（3,000〜4,000フレーム）。

## 2. 「国名だけで自動」の実態

利用者の認識は「国名を入れるとあとは自動」だが、実際に1本（例: タイ編）を作るときの作業は次のとおり。

| 工程 | 自動／人 | 実際にやったこと・判断 |
|---|---|---|
| 国の選定 | 半自動 | `candidates.py`（距離・ja.wikipedia 閲覧数・暫定の人気度）で上位30。最終判断は人（例: インドは領有権問題があるので保留） |
| 危険情報の読み取り | 自動取得＋AIが読む | 外務省ページ本文から、地域の文言・注記・理由を**原文のまま**抜き出して YAML に書く（AI）。一致検証は自動 |
| 話の筋（切り口）の決定 | **人＋AI** | 「危険地域に近い観光地」が基本。国ごとに筋が変わる（エジプト＝細い帯、タイ＝載っていない場所と30km帯、バリ島＝遠い・歴史が柱）。**ここが最も判断が要る** |
| 観光地・名物の選定 | **人＋AI** | 近さ・知名度・根拠の取りやすさ・センシティビティ。例: プレアヴィヒア寺院は領有の経緯があるのでタイ編では使わない |
| 魅力の根拠の確認 | 自動＋AI | Wikidata／ja・en Wikipedia に、キーワードが載っているか自動照合。キーワードはAIが選ぶ（`contains`） |
| 写真選び | **AI（目視）＋自動** | Commons を検索（ブラウザ経由）→ ライセンスを自動確認（CC0／PD／CC BY のみ）→ **画像を見て選ぶ**（場面と合うか、文字化けしないか） |
| 台本（読み上げ） | **人＋AI** | 型（フック3段→魅力3場面→ターン→地図→注意→結び→CTA）に沿ってAIが書き、ユーザーの言い回しの指示を反映 |
| 地図の見た目 | **AI（目視）反復** | `map.bbox`、ラベルの位置、文字の折り返しを、静止画を見て2〜4回直す |
| 読み仮名 | AI | VOICEVOX の読みを確認し、誤読はひらがな表記に直す（例: 聖→せい） |
| 検証 | 自動 | 通らなければ、文言・名前を直して再実行 |
| 書き出し・音量調整・投稿文 | 自動 | |
| 感想・修正指示 | **人** | 動画を見て、言い回し・構成・インパクトを判断 |
| 投稿・アカウント操作 | **人のみ** | 自動投稿しない（アカウント停止のリスク） |
| タグ調査・事例収集 | **人（画面確認）＋AI（集計）** | TikTok の画面でないと見られないものがある |
| 規約・利用申請 | **人のみ** | 例: JNTO の統計は、利用申請フォームが要る |

→ 汎用化の設計では、**「どこを自動化し、どこで人に判断を返すか」の境目を、最初に決める**必要がある。

## 3. ノウハウ（まだ仕組みになっていないもの）

仕組みに入っていない、対話の中で得た知見。汎用化で「どう残すか」が主題。

### 3.1 企画づくり（台本・型）

- **型の見つけ方**: ユーザーが集めたTikTok参考動画15本を、「見せ方（型）」と「必要なデータの形」で分類した（`docs/FORMATS.md`）。反応の目安（いいね数）を添えて、作る型・作らない型（会話劇・根拠のない順位）を決めた。
- **企画の核の見つけ方**: 試作（G20の危険レベル）を見て、ユーザーが挙げた「ギャップ」「特定の場所が『へー』を生む」を、シリーズの核の一言にした。**反応した理由を言語化して、企画の条件にする**。
- **失敗から学んだ条件**: 最初の案（イスタンブール）は、「危険地域と遠くて、なぜ？となる」と言われた。→「危険地域に近い観光地・名物」に絞る。
- **フック設計（ユーザーの指示で固まったもの）**: ①「危険と、隣り合わせの、観光地帯。◯◯編。」②「…知っていますか？」③「今日は、◯◯に存在する、…紹介します。」（固定の枠）。国名と背景写真だけ変えると、違う動画に見える。余計な前置き（「トルコといえばイスタンブールが有名ですが」）は削る。
- **フォローされる理由をCTAで言う**: 「世界の意外な、旅行リスクを、地図と、公的情報で、解説しています。次の地域も、紹介します。」
- **日本語で10本 → 反応を見て英語展開**（外務省の情報は海外では信頼度が読めない、という議論の結果）。
- **題材の重さで演出を変える**: 犠牲者のいる事件（バリ島）は、恐怖演出（赤黒・血・揺れ・心音）をやめる。**演出は、題材に合わせて切り替える判断が要る**。
- **国ごとに、筋が変わる**。テンプレートを埋めるだけでは、驚きが出ない国がある（タイ・バリ島）。「驚きの核は何か」を、作る前に一言で書く習慣が要る。

### 3.2 事例の共有（TikTok）

- ユーザーが事例（動画）を持ってくる → 型に分類 → 必要なデータを洗い出す → 国のオープンデータとの対応を探す、という流れ。
- 事例に添えてもらうと良い情報（今回は不足していた）: URL、いいね数、**投稿時期、再生数**、フォロワー数（反応の比較に必要）。
- **TikTok の画面でしか見られないもの**（タグのページの閲覧数、サジェスト）は、ユーザーのスクリーンショットをAIが集計する。
- ハッシュタグの仮説（`docs/SERIES.md` 8章）: 3層（シリーズ固定タグ／濃い層の固有名詞タグ／大きな枠のタグ）。ユーザーの実績（別アカウントで、小さくて濃い固有名詞のタグ3つでフォロワー1,800）が根拠。**10本の結果で見直す、という仮説段階**。
- クリエイターリワードの条件（1分以上の動画など）は、変わりうるので公式で確認する。

### 3.3 オープンデータの調査

**調べる項目（データ源ごとのチェックリスト）**
1. 提供元・URL・更新頻度
2. **商用利用の可否**（再生数収益は商用）
3. **出典表記のルール**（定型の文言があるか）
4. 取得方法（API／XML／ダウンロード。申請の要否）
5. **検証の手段**（別の系統で照合できるか）
6. 画面とナレーションに入れる「出典：〇〇（年）」の書き方

**これまでの判断**（`docs/FORMATS.md`, `docs/HANDOFF.md` 6章）
| データ | 判断 |
|---|---|
| e-Stat | 使う。商用可・出典と加工の表記が要る。appId は秘密（コード・YAML・ログに書かない） |
| 外務省 海外安全情報オープンデータ | 使う。営利・非営利を問わず利用可と明記。クレジット文言あり。**XMLのフラグが古い国がある → 公式ページ本文と照合して除外** |
| Natural Earth（地図） | 使う（パブリックドメイン） |
| Wikidata（CC0）／Wikipedia（ja・en） | 根拠の確認に使う。**同じ Wikipedia の別言語版は、独立した2系統とは言えない**と明記 |
| Wikimedia Commons（写真） | **CC0／PD／CC BY のみ**。作者・ライセンスを画面と概要欄に出す。CC BY-SA は使わない |
| 世界銀行 WDI（CC BY 4.0）、UNDP 人間開発指数（CC BY 3.0 IGO） | 使える（枠づくり用） |
| 国土地理院 地理院タイル、EDINET | 候補。条件は最終確認が要る |
| UNESCO の公式サイト | ボット対策で自動取得できない。回避しない |
| SIPRI・UN Tourism・World Happiness Report・Freedom House・民間指標 | ライセンスが混在・不明 → 使わない |
| JNTO「日本人訪問者数」 | 利用申請フォームが要る（ユーザー待ち） |

**検証の原則**（`CLAUDE.md`）
- 検証できていない数字を動画に載せない。出典URL・年・単位・読み取り方法を記録し、可能なら2系統で照合する。
- 最大／最小／全国値の妥当性をコードで確認する。
- 画面とナレーションに「出典：〇〇（年）」。
- 危険レベルは頻繁に変わる → 動画に取得日時を入れ、投稿の直前に取り直す。
- **「載っていない」ことも検証する**（地名が節に出てこないことを自動確認）。
- 距離や範囲は「地図上の概算」と明記する。

### 3.4 表現・配慮のルール

- 差別・決めつけに見える表現を避ける（宗教・民族・国）。外務省の文言のまま、評価・非難をしない。
- 領有権・紛争の敏感な題材は、扱いを事前に決める（例: プレアヴィヒア寺院）。
- 国全体が危険という誤解を避け、地域ごとに違うことを必ず伝える。
- 過去の事件を扱うときは、**現在の公式の見方（例: 2023年以降テロは発生していない）を同じ画面で伝える**。
- VOICEVOX のクレジット表記（動画内＋概要欄）。話者を変えたら表記も変える。
- 投稿文に「渡航前に外務省の最新の情報を確認してください」。

### 3.5 技術的な詰まりどころ（環境）

- Wikimedia の API／画像サーバーは共有IPで 429 になりやすい → API は1回だけ試し、ブラウザ経由に切り替える。写真は、原本ではなくサムネイルを取る。
- 公式の VOICEVOX download ツールは GitHub API が使えず失敗する → 配布物を直接取得（`scripts/setup_voicevox.sh`）。
- フォントの文字種：日本語・キリル文字は出るが、タイ文字は出ない。
- 検証で止まったときの直し方（全角・半角の違い、見出しの書き方の違い）は、コードに組み込んである。
- コンテナは一定時間で消える。`build/` は git 管理外。動画は `videos` ブランチに控える（リリース作成はこのセッション種別では許可されていない）。

## 4. 汎用化の論点（別チャットで検討したいこと）

### A. 何を「汎用」にするか（切り出しの単位）

| 単位 | 中身 | 難しさ |
|---|---|---|
| エンジン | テーマ→動画の変換（描画・音声・書き出し） | 中（グローバル状態の整理、他言語対応） |
| 検証の部品 | 出典つき主張の管理、2系統照合、原文一致、ライセンス確認 | 低〜中（考え方は共通。**最も価値が高い**） |
| データ源のアダプタ | e-Stat・外務省・Wikipedia・Commons・Natural Earth … | 低（データ源ごとに足す） |
| 企画〜調査のノウハウ | 型の見つけ方、企画の核、題材選び、事例分析、データ調査チェックリスト | 高（言語化・手順化が必要） |
| 運用 | タグ・投稿文・評価 | 中（仮説段階） |

### B. 切り出しの形（候補）

1. **別リポジトリのPythonパッケージ＋CLI**（テーマYAMLを渡して動画を出す）。データ源は、プラグインとして足す。
2. **Claude Code のスキル／スラッシュコマンド化**（「新しい題材を調査する」「テーマYAMLを書く」「検証して直す」「静止画で確認する」を手順として持たせる）。ノウハウ（3章）は、スキルの中身（チェックリスト・プロンプト）にする。
3. **ノウハウだけを先に文書化**（企画・調査のプレイブック）。コードは今のまま。
4. 1＋2（エンジンはパッケージ、進め方はスキル）。

私の見立て: **3 → 2 → 1 の順**が、手戻りが少ない。エンジンの切り出し（1）は、今のコードで十分動いているので急がなくてよい。ノウハウ（3）は、チャットが変わると失われるので、先に残す価値が高い。

### C. 人の関与（ヒューマン・イン・ザ・ループ）の設計

- 自動化しない工程を、**ゲート**として明示する（企画の核の決定、場所選び、写真の最終確認、表現の最終確認、投稿）。
- 各ゲートで、AIが人に渡す**判断材料**（候補3つ・根拠・弱点）の型を決める。今回の実績: 「案A／B／C ＋ おすすめ ＋ 確認が要ること」の形で返すと、決めやすかった。
- 「自動で作る」と「人に聞く」の線引き（例: 規約・申請・投稿・題材の重さは必ず人）。

### D. 検証層の一般化

- 動画に載せる**主張（claim）を、1件ずつ記録する**形（値・出典URL・年・単位・取得日・照合方法・結果）にして、どのテンプレートでも同じ検証を通す。
- 「通らないと動画が作れない」を、汎用エンジンの基本動作にする。
- 画面に出す出典表記も、claim から自動生成する。

### E. 他分野・他言語への展開

- 同じエンジンで、別のデータ（e-Stat の統計、EDINET、地理院の写真）を使う。
- 英語など他言語：画面文言・ナレーション・出典表記・声を差し替え。日本の外務省情報が海外で通用するかは、別途判断（`docs/SERIES.md` 9章）。

### F. 制約・リスク

- ライセンス（データ・写真・音声）と、出典表記の責任。
- TikTok の規約・アカウント停止リスク（自動投稿しない）。
- 再生数収益は商用扱い → 商用利用可否の確認が必須。
- 秘密情報（e-Stat appId）の扱い。
- 汎用化して他の人に使わせる場合の、**著作権・規約・責任の所在**（今は自分用）。

## 5. 現状から見えている「半自動化できそうな箇所」

- **YAML の下書きの自動生成**: 外務省の公式ページから、`where` / `note` / `why.evidence` の候補を原文のまま抜き出し、人が OK/NG を付ける（`docs/NEXT_SESSION.md` にも案あり）。
- **観光地の候補出し**: Wikidata の世界遺産・座標から、危険地域までの距離を計算して並べる（`data/prep/` の下準備で一部実施）。
- **写真候補の収集**: Commons の検索→ライセンス確認→コンタクトシート作成（人は一覧を見て選ぶだけ）。
- **静止画の自動チェック**: 文字のはみ出し・重なりの検出（今は目視）。
- **台本の下書き**: 型に沿った台本をAIが書き、禁止表現・誤読しやすい語を自動チェック。
- **進捗表**: 調査（`docs/prep/INDEX.md`）→ 作成 → 投稿 → 反応、を1枚で管理。

## 9. 新しいチャットで最初に決めたいこと

1. **目的**：自分用の制作ツールのままか／他の人にも使わせるか／公開（オープンソース）するか。
2. **対象**：この「政府データ×TikTok」に絞るか、他の題材・他のSNSにも広げるか。
3. **人の関与**：ユーザーが「手を動かしたくない」前提で、どのゲートまでなら判断する意思があるか（企画の核、題材、写真、表現、投稿）。
4. **切り出しの順番**：ノウハウの文書化（B-3）から始めてよいか。
5. **置き場所**：新しいリポジトリを作るか、このリポジトリの中で整理するか（環境の制約：このクラウド環境は、特定のリポジトリにだけ紐づく）。
6. **使うAI環境**：Claude Code のスキルとして持たせるか、手順書にとどめるか。
7. **最初の成果物**：例えば「企画〜調査のプレイブック」と「新しい題材を調査するときのチェックリスト」。
